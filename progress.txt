One real correctness gotcha surfaced and fixed here, worth remembering for future contract types:
C#'s compiler-synthesized record equality does NOT do deep/structural equality for collection-
typed members — `ReadingsIngested.Readings` is `IReadOnlyList<MeterReadingEnvelope>`, and the
default `EqualityComparer<IReadOnlyList<T>>` falls back to reference equality, so
`Assert.Equal(original, roundTripped)` on the whole record failed even though every element was
value-equal (System.Text.Json deserializes the array into a new List<T> instance, which is a
different reference from the original List). This is not a bug in the contract's shape — a plain
IReadOnlyList<T> is still the right public type for a collection-valued message field — it only
means naive whole-record equality assertions on any future contract with a list/array member will
have the same false-negative footgun. Fixed by asserting the scalar fields individually and

    IMPORTANT non-obvious correctness point for whoever touches this file next: `HasData` requires
    the exact same literal seed values on every model evaluation (EF diffs the "live" model against
    the migration snapshot on every startup and would treat any drift as a pending model change, and

    (random salt) or `DateTimeOffset.UtcNow`. Used a 3-arg `Pbkdf2PasswordHasher.Hash(password, salt,
    iterations)` overload with three hardcoded 16-byte salts and a fixed `SeedCreatedAt = new(2026, 1,
    1, ...)` for exactly this reason. Also had to declare `SeedCreatedAt`/the salt fields *before* the
    `Users`/`ServiceClients` list-initializer properties in the file (C# static field/property
    initializers run in textual declaration order within a type) - declaring them after would have
    silently read `SeedCreatedAt`'s zero-value default instead of the intended 2026-01-01 date.
