One real correctness gotcha surfaced and fixed here, worth remembering for future contract types:
C#'s compiler-synthesized record equality does NOT do deep/structural equality for collection-
typed members — `ReadingsIngested.Readings` is `IReadOnlyList<MeterReadingEnvelope>`, and the
default `EqualityComparer<IReadOnlyList<T>>` falls back to reference equality, so
`Assert.Equal(original, roundTripped)` on the whole record failed even though every element was
value-equal (System.Text.Json deserializes the array into a new List<T> instance, which is a
different reference from the original List). This is not a bug in the contract's shape — a plain
IReadOnlyList<T> is still the right public type for a collection-valued message field — it only
means naive whole-record equality assertions on any future contract with a list/array member will
have the same false-negative footgun. Fixed by asserting the scalar fields individually and

REAL TEST BUG FOUND (not hypothetical): first attempt asserted
`principal.FindFirst(JwtRegisteredClaimNames.Sub)?.Value` after `JwtSecurityTokenHandler.
ValidateToken` and got `null` instead of the client id - `JwtSecurityTokenHandler`'s default inbound
claim-type mapping rewrites the short JWT claim name `"sub"` to `ClaimTypes.NameIdentifier` on the
resulting `ClaimsPrincipal` (the same mapping mechanism that makes TASK-009's existing
`principal.IsInRole("Admin")` test work at all, since `"role"` gets remapped to `ClaimTypes.Role`
the same way) - so any test asserting a validated principal's claims must look them up by their
post-mapping `ClaimTypes.*` constant, not by the raw `JwtRegisteredClaimNames.*` the token was
*issued* with. Fixed by asserting `principal.FindFirst(ClaimTypes.NameIdentifier)?.Value` instead.
`scope` has no default inbound mapping (it's a non-standard short name), so `FindFirst("scope")`
correctly finds it unchanged - worth remembering this claim-mapping distinction for any future test
that validates a token through `JwtSecurityTokenHandler` rather than just decoding it unvalidated.

DESIGN DECISIONS worth not re-litigating:
  - ReadingsIngested is published BEFORE IngestAttemptRecorded. Neither publish is transactional, so
    one can be lost; readings arriving without their batch row are recoverable, whereas a batch row
    claiming a reading count whose readings never arrive is a permanent lie about what was ingested.
    The attempt record is therefore the commit marker and goes last.
  - fetchedAt is captured AFTER the HTTP call returns, not before: PRD §6 F2 defines it as the instant
    the response was received, and the Processor uses it as observed_at because the source carries no
    timestamp of its own.
  - MessageId is a fresh NewId.NextGuid() per message while BatchId is shared - the two messages are
    deduplicated independently by the processed_messages ledger (TASK-018), so sharing the
    idempotency key would make a redelivery of one look like the other.
  - error_message is truncated to 1024 chars before publishing (PRD §7.1 documents the column as
    truncated); an unbounded upstream body would otherwise be copied into every message and log line.
  - Failure outcomes are logged once per STATE CHANGE, not per attempt (PRD §6 F1). That state lives
    in the worker (a singleton) rather than the poller (scoped, new instance per cycle) - which is
    why the transition logging is IngestionWorker.ReportOutcome and not part of IngestionPoller.
  - A payload-less meter element maps to "{}" rather than throwing: JsonElement.GetRawText() throws on
    an undefined element, which would fail an entire 18-meter batch over one malformed entry.

Design (src/Processor/WeakAppHandler.Processor.{Domain,Application,Infrastructure}/...):
  - IngestionRecorder.RecordAttemptAsync/RecordReadingsAsync both funnel through one RecordAsync:

    anything else touches the connection (Postgres refuses further commands on an aborted
    transaction); the ledger is re-checked afterward - present means a genuine concurrent redelivery

    retry a faulted message on the same DbContext scope - without clearing, the retry's Add of the

    order: whichever lands first inserts a provisional row (ApplyReadingsAsync's has no HTTP status

    record - the only one that knows the real outcome - overwrites outcome/http_status/duration_ms/

A REAL correctness bug found while reading the first scaffolded migration, not a hypothetical one:
EF omits from its INSERT any property value equal to the sentinel (by default the CLR default) when
the column has a store default and lets the database fill it in. All three of §7.1's defaulted
columns are affected, and each failure is silent: hysteresis 0 -> stored as 5.00, cooldown 0 ->
stored as 300, and is_enabled false -> stored as TRUE, so TASK-030 creating a disabled rule would
have produced an enabled one. Fixed by pointing each property's sentinel at its own default value
(HasSentinel(5.00m) / (300) / (true)): the omission then writes the identical number, while 0/0/false
are sent explicitly. HasSentinel(null) does not work here - EF rejects it for non-nullable value
types. Two tests pin this down (zero/zero/false round-trip; untouched values still take the PRD
defaults).
  - HasData does NOT honour that sentinel - it is design-time and drops seed values equal to the CLR
    default independently - so the Garage rule's deliberate hysteresis of 0 was still being left to
    the column default. Fixed with the single hand-edit made to the scaffolded migration file
    (hysteresis_percent written explicitly in that row's InsertData, commented in place). The model
    snapshot already records 0, so the database and the snapshot agree and no phantom migration
    follows.

Seed rules use EF HasData with fixed ids and a fixed timestamp, following the AuthSeedData/
MetricSeedData precedent: idempotent by construction (applied once, in the migration that creates the

Shape, in src/Notification/WeakAppHandler.Notification.RuleEngine (8 files, one type each per this
repo's SA1402/SA1649 convention):
  - Its own pure input types - RuleOperator / RuleDefinition / MetricObservation /
    RuleEvaluationState - because the project must not reference the Api's domain types or Contracts.
    RuleOperator duplicates AlertOperator's members deliberately; the Api will map between them
    (TASK-029), and the duplication is what keeps a persistence concern from leaking into the engine.
  - ThresholdNumeric and MetricObservation.Numeric are decimal, not double: the threshold column is
    numeric(12,4), and comparing a binary float against it would make the engine and the database
    disagree about what "exactly at the threshold" means - one of the two boundary cases the task
    explicitly asks to be tested. TASK-029 converts ReadingStored's double once, at the boundary.
  - No clock: MetricObservation.ObservedAt is also the instant cooldown is measured from, so every
    decision is reproducible from its arguments alone. That is what makes the boundary cases
    arithmetic rather than integration scenarios.
  - AlertRuleEngine.Evaluate returns RuleDecision { Kind, Reason, IsBreaching }. Kind is what to do
    (None/Raise/Resolve); Reason (Raised/Resolved/NotApplicable/NoTransition/AlertAlreadyActive/
    CooldownActive/WithinHysteresisBand/NotBreaching) exists because "no alert" has seven very
    different causes, and telling them apart is the difference between a working suppression policy
    and a lost alert - the tests assert on Reason, since the mere absence of an alert satisfies every
    branch equally. IsBreaching is returned rather than left to the caller to recompute: it is exactly
    what belongs in alert_rule_state.was_breaching, and a caller deriving it a second time could
    disagree with the decision it is storing it alongside.
  - AlertRuleEngine.Matches covers rule scoping (enabled + metric + optional location/meterType where
    null means any). Case-insensitive on purpose: those strings pass through the wire payload, the
    Processor's meter registration and an operator typing into the TASK-030 form, and a rule that
    matches nothing because of a capital letter produces no alerts AND no errors.

Four decisions worth knowing before TASK-029 builds on this:
  1. wasBreaching is read from persisted state, NOT recomputed from the event's previousValue the way
     PRD 6.6's pseudocode does. After a restart the previous value is whatever the next poll happens
     to report, while the stored flag still knows the window is open - so the pseudocode's version
     would re-raise an alert for a breach that is already active.
  2. A transition swallowed by cooldown still records the breach, so the alert is DROPPED, not queued.
     The alternative (leaving was_breaching false) fires the moment the window closes, which turns a
     rate limit into a delayed duplicate. Pinned by
     Evaluate_BreachSwallowedByCooldown_DoesNotFireLateOnTheNextReading.
  3. The hysteresis band's direction follows the operator: an upper bound (gt/gte) clears downwards at
     threshold - margin, a lower bound (lt/lte) clears upwards at threshold + margin, and eq clears
     symmetrically once |value - threshold| >= margin. Getting the sign wrong on the lt family is the
     classic form of this bug and it is SILENT - the band lands on the breaching side, so the alert
     resolves the instant it stops breaching and hysteresis appears to be configured while doing
     nothing. The margin is a percentage of the threshold's MAGNITUDE (Math.Abs), so a negative
     threshold keeps its band on the correct side; a zero threshold has a zero band by construction.
  4. NotApplicable is a third answer, distinct from breaching and not-breaching, and it leaves
     was_breaching untouched instead of writing false - clearing it there would fake a transition on
     the next reading that can actually be compared. It covers: a numeric rule against a boolean
     metric and the reverse, a rule with both or neither threshold (the check constraint should
     prevent that - the engine refuses to guess rather than hide a bypassed constraint), and any
     ordering operator on a boolean rule. That last one matters: `false < true` is true in CLR terms,
     so a naive comparison would make an `lt true` rule on motion breach on every quiet poll.

Boolean metrics have no band at all - they resolve as soon as the value stops matching, whatever
hysteresis_percent happens to say, so a stray margin cannot trap the Garage motion alert open forever.

Decisions worth not undoing without reading why:
  1. Rule scoping is decided in memory by AlertRuleEngine.Matches, NOT filtered in SQL. Matching is
     case-insensitive in the engine; a SQL `metric_code = @p` would quietly disagree, and the symptom
     of that disagreement is a MISSING alert with no error anywhere. The query narrows on is_enabled
     only. The rule set is hand-authored and tiny; if it stops being tiny the answer is a cache
     invalidated by TASK-030's CRUD, not a filter that can drift from the engine.
  2. Deliberately NO processed_messages ledger in this service. A redelivered ReadingStored is
     harmless by construction: the second evaluation reads was_breaching = true and an open alert from
     the database, so the engine answers NoTransition/AlertAlreadyActive. The partial unique index on
     active alerts is the backstop for two deliveries that overlap rather than follow one another, and
     SaveAsync clears the change tracker on DbUpdateException so MassTransit's retry - which reuses
     the same scope - can actually re-read and succeed.
  3. triggered_at / resolved_at / last_evaluated_at all come from ReadingStored.ObservedAt, never from
     a clock. The engine measures cooldown from the observation's own instant, so a cooldown recorded
     against wall time would drift by exactly the queue's latency.
  4. A NotApplicable decision writes NO alert_rule_state row at all, rather than one saying "not
     breaching": storing a breach flag the engine never computed would fake a transition on the first
     reading that really can be compared.
  5. AlertRuleMapping converts ReadingStored's double to decimal at the boundary and answers null for
     a non-finite value or one outside numeric(12,4)'s range - checked BEFORE the cast, because
     casting a double above decimal.MaxValue throws. Null makes every numeric rule report
     NotApplicable, a far better outcome than faulting the message into the DLQ on arithmetic.
  6. AlertResolved carries the severity the ALERT was raised under, AlertRaised the rule's current
     one. The two differ the moment an operator edits a rule while its alert is open.
